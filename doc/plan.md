# 개발 계획 및 팀원 역할 분담

## 1. 팀 구성

| 이름 | 역할 |
|---|---|
| 문태웅 | 프론트엔드(React) 전체, Community MCP + 커뮤니티(FGI) 데이터 파이프라인, 통합 테스트·운영 |
| 권오현 | 전체 기획·아키텍처·계약 문서, MCP Client(Agent Workflow), Price MCP(한국투자증권), 발표자 |
| 윤기화 | Backend(인증·Memory·개인화·분석 API), DB·infra, News MCP |
| 김인혜 | Disclosure MCP(OpenDART 수집·사업보고서 RAG·pgvector) |
| 박성엽 | 사용자 관점 검수·피드백(화면 흐름 점검, 문구·설명 검토, 발표 리허설 피드백) |

팀은 화면, 사용자·저장소, 분석 오케스트레이션, 데이터 제공 서버를 독립된 실행 단위로 나눠 개발합니다. 각 실행 단위의 연결은 `shared/CONNECTION_CONTRACT.md`와 `shared/contracts/`를 기준으로 맞춥니다.

---

## 2. 작업 5덩어리

프로젝트를 아래 5덩어리로 나눴습니다. 구현 파일의 주 담당을 구분하고, 공통 계약을 먼저 확정해 각 서버를 동시에 개발할 수 있게 구성했습니다.

| 덩어리 | 담당 | 범위 |
|---|---|---|
| ① 사용자 화면·Community·운영 | 문태웅 | React 단일 페이지, 마스코트·반응형 화면, Community MCP, FGI 데이터 파이프라인, 배포·통합 테스트 |
| ② 기획·오케스트레이션·가격 | 권오현 | 서비스 기획, 전체 아키텍처와 연결 계약, MCP Client Agent Workflow, Price MCP(KIS), 발표 |
| ③ 사용자·저장소·뉴스 | 윤기화 | FastAPI Backend, JWT 인증, 투자 성향·Memory·개인화 응답, PostgreSQL·Redis·Docker Compose, News MCP |
| ④ 공시·사업보고서 RAG | 김인혜 | Disclosure MCP, OpenDART 수집, 사업보고서 파싱·청킹·임베딩, pgvector 검색 |
| ⑤ 사용자 관점 검수 | 박성엽 | 화면 흐름 점검, 문구·설명 검토, 사용성 피드백, 발표 리허설 피드백 |

**연결 계약은 구현보다 먼저 고정합니다.** 일곱 서비스가 서로 다른 프로세스로 실행되므로 포트, Endpoint, Tool 이름, JSON 필드가 바뀌면 여러 담당자의 작업이 동시에 영향을 받습니다.

## 3. 파트별 상세

### ① 사용자 화면·Community·운영 — 문태웅

| 항목 | 내용 |
|---|---|
| 맡는 파일 | `frontend/`, `mcp_servers/community_mcp/`, 운영 설정 |
| 산출물 | React 검색·결과·로그인 화면, 상태형 SVG 마스코트, 커뮤니티 반응·FGI Tool, 데모 환경, 통합 검증 |
| 화면 범위 | 검색 히어로 → 가격·한 줄 결론 → 비회원 게이트 → 회원 근거 → 성향별 확인 포인트의 단일 페이지 흐름과 `/login` |
| 데이터 범위 | 네이버 종목토론방 집계를 제공하는 FGI API를 Community MCP에서 조회·정규화하고, 원문 전체 대신 집계·주제·짧은 대표 근거만 전달합니다 |
| 완료 기준 | 데스크톱과 390px 화면에서 가로 스크롤 없이 주요 상태가 표시되고, 비회원·회원·미지원·부분 실패·전체 실패 흐름을 확인할 수 있습니다. 통합 환경에서 Frontend부터 네 MCP까지 한 요청이 왕복합니다 |

### ② 기획·오케스트레이션·가격 — 권오현

| 항목 | 내용 |
|---|---|
| 맡는 파일 | `docs/`, `shared/`, `mcp_client/`, `mcp_servers/price_mcp/` |
| 산출물 | 최종 아키텍처, 서비스 연결 계약, 단일 Stock Analysis Agent Workflow, Price MCP, 발표 자료와 시연 흐름 |
| 기본 Workflow | 현재가, 최근 뉴스, 최근 공시, 사업보고서 검색, 커뮤니티 반응의 5개 Tool을 결정적으로 병렬 호출합니다 |
| Agent 경계 | 기본 조회 결과를 설명하고, 필요한 경우 기본 목록에 있는 접수번호의 `get_disclosure_detail`만 최대 2건 추가 조회합니다. 최대 3단계에서 종료합니다 |
| 가격 범위 | 한국투자증권 실전투자 REST 현재가를 조회하고 종목별 60초 캐시를 적용합니다. 실제 API 실패를 가짜 가격으로 대체하지 않습니다 |
| 완료 기준 | `POST /internal/v1/common-analyses`가 규칙 기반 관심 온도·근거 수준과 Agent 설명을 계약 형식으로 반환합니다. 현재가 실패는 전체 실패, 나머지 Tool 실패는 확인된 자료를 유지한 부분 성공으로 구분합니다 |

### ③ 사용자·저장소·뉴스 — 윤기화

| 항목 | 내용 |
|---|---|
| 맡는 파일 | `backend/`, `db/`, `infra/`, `mcp_servers/news_mcp/` |
| 산출물 | JWT 로그인, 데모 사용자 10명, 투자 성향, 장·단기 Memory, 분석 API, 분석 이력, PostgreSQL·Redis Compose, News MCP |
| Backend 경계 | Frontend의 유일한 서버 진입점으로 지원 종목 확인, 회원 구분, 성향 조회, MCP Client 호출, 공개·회원 응답 조립을 담당합니다 |
| 저장 범위 | PostgreSQL에는 사용자·성향·분석 실행 이력을 저장하고 Redis에는 최근 검색 상태를 TTL과 함께 저장합니다 |
| 뉴스 범위 | NAVER API HUB 뉴스 검색 결과를 정제하고 최근 자료 우선 최대 10건을 반환합니다. 기사 본문 전체 크롤링은 범위에서 제외합니다 |
| 완료 기준 | 비회원과 회원의 공개 범위가 분리되고, JWT·성향·Memory가 사용자별로 섞이지 않습니다. `db/schema.sql`과 `db/seed.sql`이 Compose 최초 실행 때 적용됩니다 |

### ④ 공시·사업보고서 RAG — 김인혜

| 항목 | 내용 |
|---|---|
| 맡는 파일 | `mcp_servers/disclosure_mcp/` |
| 산출물 | 최근 공시·공시 상세·사업보고서 검색·정기보고서 유형별 검색 Tool, OpenDART 수집기, 보고서 파서·청커, pgvector 저장·검색 |
| 수집 범위 | 지원 20종목의 기업코드를 동기화하고 최근 공시 메타데이터와 최신 연간 사업보고서를 다룹니다 |
| 검색 방식 | 기업·보고서 연도를 SQL로 먼저 좁힌 뒤 `text-embedding-3-small` 1536차원 벡터로 관련 구절을 검색해 최대 5개만 반환합니다 |
| 완료 기준 | `get_recent_disclosures`, `get_disclosure_detail`, `search_annual_report`, `search_periodic_report`가 현재 Tool 계약을 지키며, DART 원문 전체가 아니라 필요한 메타데이터·상세·관련 구절만 MCP Client로 전달됩니다 |

### ⑤ 사용자 관점 검수 — 박성엽

| 항목 | 내용 |
|---|---|
| 검수 대상 | 검색 시작점, 분석 대기, 공개 결과, 로그인 게이트, 회원 근거, 성향별 확인 포인트, 미지원·오류 안내, 발표 시연 흐름 |
| 주요 산출물 | 화면 흐름 점검표, 이해하기 어려운 문구와 설명에 대한 피드백, 리허설 관찰 결과 |
| 검수 원칙 | 투자 추천으로 오해할 표현, 데이터 부족을 숨기는 표현, 회원·비회원 경계가 불분명한 동작을 우선 확인합니다 |
| 완료 기준 | 처음 보는 사용자가 검색부터 근거 확인까지 막힘없이 진행하고, 관심 온도가 상승 가능성이나 추천 점수가 아님을 이해할 수 있습니다 |

## 4. 발표 준비 — 권오현(발표자)

개발과 별개로 발표자가 전체 흐름을 하나의 이야기로 연결하고, 박성엽이 사용자 관점에서 리허설 피드백을 제공합니다.

| 항목 | 내용 |
|---|---|
| 발표 구성 | 문제와 목적 → 일곱 서비스 구조 → 네 MCP 데이터 흐름 → Workflow와 Agent 경계 → Memory 개인화 → 실제 데모 → 한계 |
| 시연 대본 | 비회원 삼성전자 검색 → `왜 이렇게 판단했나요?` 게이트 → 데모 계정 로그인 → 근거·출처 → 성향별 확인 포인트 → 미지원 종목 순서로 고정합니다 |
| 기술 포인트 | Frontend는 Backend만 호출하고, MCP Client가 네 MCP를 통합하며, Agent는 읽기 전용 공시 상세 Tool만 제한적으로 사용한다는 경계를 설명합니다 |
| 리허설 | 실제 연결된 데모 환경에서 최소 2회 진행합니다. 박성엽은 화면 전환, 문구 이해도, 설명 속도와 질문 가능 지점을 기록해 발표자에게 전달합니다 |
| 사전 점검 | 발표 전 Frontend, Backend, MCP Client, MCP 4개의 `/health` 또는 상태 주소를 확인하고 삼성전자 전체 왕복을 실행합니다 |
| 안전망 | 네트워크·일부 MCP 실패 시 부분 성공 표시와 규칙 기반 문장 폴백을 설명합니다. 가격이 없으면 분석을 중단한다는 경계도 함께 안내합니다 |

## 5. 협업 규칙

| 규칙 | 내용 |
|---|---|
| 브랜치 | `main`은 통합이 끝난 상태로 유지합니다. 기능 작업은 별도 브랜치에서 진행하고 PR 리뷰 후 병합합니다 |
| 담당 범위 | 서비스별 폴더 주 담당을 지킵니다. 다른 담당의 파일을 바꿔야 하면 영향 범위와 계약 변경을 먼저 공유합니다 |
| 연결 계약 | 포트·Endpoint·Tool·필드 변경은 `shared/CONNECTION_CONTRACT.md`와 `shared/contracts/`에서 먼저 합의하고 구현·테스트·문서를 함께 갱신합니다 |
| 사용자 정보 | MCP Client에는 성향 네 값만 전달할 수 있으며 사용자 ID·비밀번호·JWT·개인정보는 전달하지 않습니다. MCP 서버에는 성향도 전달하지 않습니다 |
| 비밀 값 | 실제 `.env`, API Key, DB 비밀번호, 토큰은 커밋하지 않습니다. `.env.example`에는 이름과 예시 형식만 둡니다 |
| 데이터 표현 | 확인하지 못한 값은 추측해 채우지 않습니다. 일부 소스 실패는 `partial_success`와 실패 목록으로 그대로 드러냅니다 |
| 테스트 | 서비스 단위 테스트 → 계약 테스트 → MCP 연결 → Backend 연결 → Frontend 시나리오 순으로 확인합니다 |
| 리뷰 | 구현 담당자는 계약과 코드의 일치를 확인하고, 사용자 문구와 화면 흐름은 박성엽의 검수 결과를 반영합니다 |
