# Frontend 개발 방향 제안서

> 이 문서는 팀 회의를 위한 Frontend 설계 예시입니다. 현재 Streamlit을 기준으로 작성했으며, 화면 구성과 컴포넌트 분리는 팀 합의 후 확정합니다.

## 1. Frontend의 목표

Frontend의 핵심은 많은 정보를 한 화면에 채우는 것이 아니라 사용자가 다음 질문에 빠르게 답을 얻도록 만드는 것이다.

> `이 종목이 왜 움직였고, 시장은 어떻게 반응하고 있으며, 그 반응에 확인된 근거가 있는가?`

Frontend는 분석 로직, DB 조회, 외부 API 호출을 직접 수행하지 않는다. 모든 업무 요청은 Backend API를 통해 진행한다.

## 2. 대표 화면 흐름

```text
로그인
  → 종목 검색
  → 종목 시장 온도 화면
  → 가격·수급·뉴스·공시 근거 확인
  → AI 질문
  → 투자 메모 저장
```

첫 화면부터 게시글, 포트폴리오, 복잡한 차트를 모두 보여주기보다 위 흐름을 우선 완성한다.

## 3. 화면 구성 제안

### 3.1 로그인·회원가입

- 이메일 또는 사용자명
- 비밀번호
- 로그인 상태 표시
- 권한에 따라 관리자 메뉴 표시

### 3.2 종목 검색

- 기업명·종목코드 검색 입력
- 자동완성 결과
- 최근 검색 종목
- 관심 종목
- 데이터 마지막 갱신 시각

### 3.3 종목 분석 화면

상단부터 다음 순서로 배치하는 방향을 제안한다.

1. 종목명, 종목코드, 현재가, 등락률
2. 시장 심리 온도
3. 근거 강도
4. 가격·거래량 차트
5. 개인·외국인·기관 수급
6. 주요 이슈와 커뮤니티 주제
7. 최신 뉴스와 공시
8. AI 질문 영역
9. 사용자 투자 메모

### 3.4 관리자 화면

- PDF·MP3·MOV 업로드
- 종목과 문서 종류 선택
- 제목, 기준일, 출처 입력
- 청크 크기와 겹침 범위 설정
- 처리 상태 확인
- 등록 문서와 청크 삭제

## 4. 가장 중요한 화면: 시장 온도 카드

검색 결과의 중심은 시장 심리 온도와 근거 강도다.

```text
삼성전자 005930
현재가 / 등락률 / 데이터 기준 시각

시장 심리 온도: 82 · 탐욕
- 긍정 표현과 게시글 수 증가
- 가격과 거래량 동반 상승
- 개인 순매수 증가

근거 강도: 46 · 보통 이하
- 관련 뉴스 다수
- 신규 공식 공시는 확인되지 않음
- 외국인·기관 순매도

해석
시장 기대가 빠르게 상승했지만 확인된 공식 근거는 제한적입니다.
```

점수만 강조하지 않고 이유와 기준 시각을 같은 영역에 표시한다.

## 5. Frontend 폴더 구조 예시

현재 `app.py`에서 시작하되 화면이 늘어나면 다음처럼 분리하는 방안을 논의할 수 있다.

```text
frontend/
├─ .env.example
├─ requirements.txt
├─ app.py                    # 앱 시작, 공통 설정
├─ pages/
│  ├─ login.py
│  ├─ stock_dashboard.py
│  ├─ my_notes.py
│  └─ admin_documents.py
├─ components/
│  ├─ stock_search.py
│  ├─ market_header.py
│  ├─ sentiment_card.py
│  ├─ evidence_card.py
│  ├─ flow_chart.py
│  ├─ source_list.py
│  ├─ analysis_chat.py
│  └─ progress_panel.py
├─ services/
│  ├─ api_client.py           # Backend HTTP 요청
│  ├─ auth_client.py
│  └─ sse_client.py
├─ state/
│  └─ session.py              # 로그인·선택 종목·분석 상태
└─ models/
   ├─ stock.py
   └─ analysis.py
```

폴더는 실제 화면이 추가되는 시점에 나누고, 빈 구조를 과도하게 만들지 않는다.

## 6. Backend 연동 원칙

- Backend 주소는 환경변수로 관리한다.
- API 요청 코드는 `api_client` 같은 한 위치에 모은다.
- 화면 코드에서 직접 URL 문자열을 반복하지 않는다.
- 요청 성공, 조회 결과 없음, 서버 오류를 구분한다.
- 모든 화면에서 `observed_at` 또는 `updated_at`을 표시한다.
- Frontend는 Backend 응답을 임의로 재해석하지 않는다.
- 점수 계산은 Frontend가 아니라 Backend 또는 데이터 처리 영역에서 수행한다.

## 7. 상태 관리 항목

최소한 다음 상태가 필요하다.

- 로그인 사용자와 권한
- 인증 정보
- 현재 선택한 종목
- 기본 분석 기간
- 진행 중인 `analysis_id`
- SSE 연결 상태
- 마지막 정상 분석 결과
- 사용자 투자 메모 임시 입력

화면을 이동하거나 새로고침했을 때 분석 결과를 다시 조회할 수 있도록 `analysis_id`를 기준으로 복구하는 방향을 고려한다.

## 8. SSE 사용자 경험

분석 요청 후 빈 화면에서 기다리게 하지 않고, Backend가 보내는 이벤트를 사용자 문장으로 표현한다.

```text
종목을 확인하고 있습니다.
가격과 수급을 불러오고 있습니다.
최근 뉴스를 찾고 있습니다.
DART 공시를 확인하고 있습니다.
커뮤니티 분위기를 분석하고 있습니다.
근거를 바탕으로 답변을 작성하고 있습니다.
```

오류가 발생하면 전체 실패로만 표시하지 않고 어떤 자료를 가져오지 못했는지 알려준다.

예시:

> 커뮤니티 데이터는 가져오지 못했습니다. 가격·수급·뉴스·공시 자료를 기준으로 제한된 분석을 제공합니다.

## 9. 차트와 정보 표현 원칙

- 상승은 무조건 긍정, 하락은 무조건 부정으로 표현하지 않는다.
- 색상만으로 상태를 전달하지 않고 텍스트 라벨을 함께 표시한다.
- 가격 차트와 수급 차트의 기준 기간을 맞춘다.
- 숫자에는 단위와 기준 시각을 표시한다.
- 뉴스와 공시는 제목, 출처, 발행 시각, 원문 연결을 제공한다.
- 커뮤니티 내용은 사실이 아닌 `시장 반응`으로 명확히 표시한다.
- AI 답변은 `확인된 사실`, `시장 반응`, `해석`, `주의점`, `출처`로 구분한다.

## 10. 사용자 투자 메모 화면

자유 입력 하나만 제공하기보다 다음 항목을 나누는 방향을 제안한다.

- 매수 또는 관심 근거
- 우려 요소
- 앞으로 확인할 조건
- 메모 작성 시점의 가격
- 메모 작성일

사용자는 저장된 메모를 기반으로 다음 질문을 할 수 있다.

- 이전 매수 근거가 아직 유효한가?
- 내가 걱정한 위험 요소와 관련된 최근 공시가 있는가?
- 이전 분석과 현재 시장 심리가 어떻게 달라졌는가?

## 11. Frontend 개발 순서 제안

1. Backend 연결 상태 표시
2. 샘플 종목 검색
3. 샘플 시장 온도 카드
4. 가격·수급·뉴스·공시 섹션
5. 실제 Backend 응답 Schema 연동
6. 분석 요청과 SSE 진행 표시
7. 로그인·권한
8. 투자 메모
9. 관리자 자료 등록
10. 반응형 배치와 시각적 정리

화면 디자인을 먼저 완성하기보다 샘플 데이터 → 실제 API 데이터 순서로 연결한다.

## 12. Frontend MVP 완료 기준

- 사용자가 로그인할 수 있다.
- 종목명 또는 종목코드로 검색할 수 있다.
- 시장 심리 온도와 근거 강도를 이유와 함께 볼 수 있다.
- 가격·수급·뉴스·공시를 구분해서 확인할 수 있다.
- AI 분석을 요청하고 진행 과정을 볼 수 있다.
- 답변의 출처와 데이터 기준 시각을 확인할 수 있다.
- 투자 메모를 작성하고 다시 불러올 수 있다.
- 일부 데이터가 누락되어도 화면 전체가 중단되지 않는다.

## 13. Frontend 회의 질문

- 첫 화면을 검색 중심으로 할지 관심 종목 중심으로 할지
- 시장 심리 온도와 근거 강도를 어떤 형태로 표현할지
- 가격·수급 차트의 기본 기간을 무엇으로 할지
- 뉴스·공시·커뮤니티를 탭으로 나눌지 한 화면에 배치할지
- AI 질문 영역을 고정할지 별도 페이지로 분리할지
- Streamlit에서 SSE를 어떤 사용자 경험으로 구현할지
- 모바일 화면을 MVP에 포함할지
- 관리자 화면을 어느 범위까지 구현할지
