# Database 개발 방향 제안서

> **보관용 초기 문서:** 자유 질문과 장기 대화 저장 후보가 포함된 과거 초안이다. 현재 범위는 `db/GUIDE.md`, `backend/MEMORY_GUIDE.md`, `shared/contracts/`를 따른다.

> 이 문서는 팀 회의를 위한 Database 설계 예시입니다. 현재 `schema.sql`의 원칙을 유지하면서 필요한 데이터를 검토한 초안이며, 실제 테이블과 컬럼은 데이터 제공처 및 API 응답을 확인한 뒤 확정합니다.

## 1. DB 설계 핵심 원칙

현재 프로젝트의 다음 원칙을 유지한다.

> 숫자·상태·날짜·관계는 일반 테이블에 저장하고, 의미 기반 검색이 필요한 긴 텍스트만 pgvector에 저장한다.

### 일반 테이블이 적합한 질문

- 삼성전자 현재가는 얼마인가?
- 최근 7일 동안 몇 퍼센트 움직였는가?
- 개인·외국인·기관 순매수는 얼마인가?
- 사용자의 보유 수량과 평균 가격은 얼마인가?

### 벡터 검색이 적합한 질문

- 최근 뉴스에서 가장 많이 언급되는 위험 요소는 무엇인가?
- 사업보고서에서 파운드리 관련 우려를 찾아줘.
- 내 이전 매수 근거와 현재 뉴스를 비교해줘.

## 2. 현재 존재하는 테이블

현재 `schema.sql`에는 다음 구조가 있다.

| 테이블 | 현재 역할 |
|---|---|
| `users` | 사용자 기본정보 |
| `positions` | 사용자 보유 종목 |
| `transactions` | 사용자 거래 기록 |
| `fear_greed_daily` | 종목별 일간 공포·탐욕 점수 |
| `rag_chunks` | 뉴스·공시·커뮤니티·메모·리포트 청크와 임베딩 |

이 구조는 초기 방향과 잘 맞지만 로그인, 종목 마스터, 수급, 원문 관리, 분석 기록 등을 위해 확장이 필요하다.

## 3. 논의할 데이터 영역

### 3.1 사용자와 권한

`users`에 다음 개념이 필요하다.

- 로그인 식별자
- 비밀번호 해시
- 사용자 표시 이름
- 역할: `admin` 또는 `user`
- 계정 상태
- 생성일·수정일·마지막 로그인 시각

실제 비밀번호는 저장하지 않고 안전한 해시만 저장한다.

### 3.2 종목 마스터

`stocks` 테이블 예시:

- `stock_code`
- `stock_name`
- 시장 구분
- 업종
- DART 기업 고유번호
- 검색 별칭
- 상장 상태
- 마지막 갱신 시각

다른 테이블은 종목명을 반복 저장하기보다 가능한 범위에서 종목코드를 기준으로 연결한다.

### 3.3 가격·거래량

조회 제공처와 저장 전략에 따라 다음 중 하나를 선택한다.

- 현재가는 외부 API와 Redis 캐시만 사용
- 발표용·분석용 가격 시계열은 PostgreSQL에도 저장

가격 시계열을 저장한다면 필요한 값은 다음과 같다.

- 종목코드
- 기준 시각 또는 거래일
- 시가·고가·저가·종가
- 거래량
- 데이터 간격
- 데이터 제공처
- 수집 시각

같은 종목·같은 기준 시각·같은 간격의 데이터가 중복 저장되지 않도록 유일 조건이 필요하다.

### 3.4 투자자별 수급

`investor_flows` 테이블 예시:

- 종목코드
- 거래일 또는 기준 시각
- 투자자 유형: 개인·외국인·기관
- 순매수 수량
- 순매수 금액
- 데이터 제공처
- 수집 시각

제공되는 수급 데이터가 장중인지 장 마감 후 확정치인지 구분할 수 있어야 한다.

### 3.5 원문 문서

긴 문서를 바로 `rag_chunks`에만 저장하면 원본 관리와 재임베딩이 어려울 수 있다. 원문 단위의 `source_documents`를 두는 방안을 제안한다.

필요한 정보 예시:

- 문서 ID
- 종목코드
- 문서 종류: 뉴스·공시·커뮤니티 요약·리포트·멀티모달 전사
- 원문 식별자
- 제목
- 원문 또는 정제 본문
- 출처와 URL
- 발행 시각
- 수집 시각
- 본문 해시
- 처리 상태
- 메타데이터

`rag_chunks`는 `source_documents`의 문서 ID를 참조하여 청크와 원문의 관계를 유지하는 방향을 검토한다.

### 3.6 사용자 투자 메모

현재는 사용자 메모를 `rag_chunks`에 직접 넣고 있다. 수정·삭제·목록 조회가 필요하다면 원본 메모를 일반 테이블로 관리하고, 검색용 청크만 `rag_chunks`에 생성하는 방향이 더 명확하다.

`user_notes` 예시:

- 사용자 ID
- 종목코드
- 메모 종류: 매수 근거·우려·확인 조건·일반 메모
- 제목
- 내용
- 작성 시점 가격
- 생성일·수정일
- 삭제 여부

메모가 수정되면 관련 임베딩도 다시 생성해야 한다.

### 3.7 시장 심리와 근거 강도

현재 `fear_greed_daily`를 확장하거나 별도의 `market_sentiment_snapshots`를 두는 방향을 검토한다.

필요한 값 예시:

- 종목코드
- 기준 시각 또는 날짜
- 시장 심리 온도
- 심리 라벨
- 근거 강도
- 근거 라벨
- 분석 게시글 수
- 긍정·부정·중립 비율
- 게시글 증가율
- 계산 버전
- 계산 이유 JSON
- 데이터 기준 시각

점수 계산식이 바뀔 수 있으므로 `calculation_version`을 저장하는 것이 좋다.

### 3.8 분석 실행과 근거

AI 답변이 어떤 자료를 사용했는지 추적하기 위해 `analysis_runs`와 `analysis_evidence`를 검토한다.

`analysis_runs` 예시:

- 분석 ID
- 사용자 ID
- 종목코드
- 질문
- 상태
- 최종 답변
- 사용 모델
- 데이터 기준 시각
- 생성일·완료일
- 오류 정보

`analysis_evidence` 예시:

- 분석 ID
- 근거 종류
- 원문 또는 청크 ID
- 제목
- 출처
- 사용 순서

이 구조가 있으면 발표에서 `AI가 어떤 근거로 답했는지`를 설명할 수 있고, 오류도 추적하기 쉽다.

## 4. 테이블 관계 개념도

```text
users
  ├─ positions
  ├─ transactions
  ├─ user_notes ─────┐
  └─ analysis_runs   │
          └─ analysis_evidence
                     │
stocks               │
  ├─ price_data      │
  ├─ investor_flows  │
  ├─ sentiment_snapshots
  ├─ source_documents
  │       └─ rag_chunks
  └────────────── user_notes
```

실제 외래키와 삭제 규칙은 개인정보, 원문 보존 정책, 재수집 가능성을 고려해 결정한다.

## 5. `rag_chunks` 사용 규칙

현재 `doc_type`은 다음 용도로 사용할 수 있다.

- `user_note`
- `news`
- `disclosure`
- `community_summary`
- `report`
- 멀티모달을 적용한다면 `ir_transcript` 등의 추가 종류 검토

### 필수 검색 순서

1. `stock_code`로 종목을 제한한다.
2. `doc_type`으로 자료 종류를 제한한다.
3. 사용자 메모는 `user_id`로 제한한다.
4. 질문 기간에 맞게 `published_at`을 제한한다.
5. 그 범위 안에서 벡터 유사도 top-k를 계산한다.

### 청크 관리

- 원문 문서와 청크 관계를 유지한다.
- `content_hash`로 중복을 방지한다.
- 임베딩 모델명과 차원을 기록한다.
- 청크 크기와 겹침 범위를 메타데이터에 남긴다.
- 문서 삭제 시 관련 청크도 함께 처리한다.
- 원문 수정 시 기존 청크를 무효화하고 다시 임베딩한다.

## 6. PostgreSQL과 Redis의 구분

| 데이터 | PostgreSQL | Redis |
|---|---|---|
| 사용자·권한 | 영구 저장 | 세션 사용 시 일부 |
| 관심 종목·메모 | 영구 저장 | 필요 시 최근 조회 캐시 |
| 현재가 | 필요 시 시계열 저장 | 짧은 캐시 |
| 뉴스·공시 원문 | 영구 저장 | 최신 목록 캐시 |
| RAG 청크 | 영구 저장 | 일반적으로 저장하지 않음 |
| 분석 답변 | 영구 기록 | 동일 질문 단기 캐시 |
| 분석 진행 상태 | 최종 상태 저장 | 실시간 진행 상태 |

Redis 데이터가 사라져도 사용자 계정, 메모, 원문, 최종 분석 결과가 유실되지 않아야 한다.

## 7. 데이터 갱신과 중복 처리

각 데이터에 원문 식별자와 수집 시각을 기록한다.

| 데이터 | 중복 기준 예시 |
|---|---|
| 종목 | 종목코드 |
| 가격 | 종목코드 + 기준 시각 + 간격 |
| 수급 | 종목코드 + 거래일 + 투자자 유형 |
| 뉴스 | 원문 URL 또는 정규화 본문 해시 |
| DART 공시 | 접수번호 |
| 커뮤니티 | 원문 게시글 ID 또는 요약 날짜 |
| RAG 청크 | 문서 ID + 청크 번호 또는 내용 해시 |

같은 뉴스가 여러 언론사에서 반복된 경우 원문 중복과 동일 이슈 묶음을 별도로 구분할 필요가 있다.

## 8. 데이터 기준 시각

사용자에게 오래된 데이터를 최신처럼 보여주지 않도록 다음 시각을 구분한다.

- 원문이 발표된 시각
- 외부 데이터가 기준으로 삼는 시각
- 우리 시스템이 수집한 시각
- 분석을 생성한 시각

특히 수급과 가격은 실시간 값인지 장 마감 후 확정 값인지 표시해야 한다.

## 9. 개인정보와 권한

- 사용자 메모와 보유정보는 사용자별로 분리한다.
- 관리자도 필요한 범위에서만 사용자 정보를 조회한다.
- 비밀번호는 해시만 저장한다.
- 사용자 메모 RAG 검색에는 반드시 사용자 ID 조건을 적용한다.
- 질문·답변 기록의 보존 기간과 삭제 방식을 합의한다.
- 관리자 문서와 사용자 개인 문서를 구분한다.

## 10. 인덱스 방향

데이터가 적은 초기에는 복잡한 최적화보다 정확한 조건 검색을 우선한다.

검토할 일반 인덱스:

- 종목코드 + 기준 날짜
- 종목코드 + 문서 종류 + 발행일
- 사용자 ID + 종목코드
- 분석 상태 + 생성일
- 원문 식별자와 내용 해시

벡터 ANN 인덱스는 데이터가 충분히 커지고 실제 성능 문제가 확인된 뒤 적용한다. 현재 스키마의 설명처럼 초기에는 제한된 범위의 정확한 검색이 더 중요하다.

## 11. 마이그레이션과 시드 데이터

- 스키마 변경을 팀원이 같은 순서로 적용할 수 있는 방식을 정한다.
- 삼성전자 데모 데이터는 반복 실행해도 중복되지 않아야 한다.
- 시드에는 사용자, 종목, 가격, 수급, 뉴스, 공시, 커뮤니티 요약, 사용자 메모의 최소 예시를 포함하는 방향을 검토한다.
- 실제 API 연동 전에도 전체 연결 테스트가 가능하도록 샘플 데이터를 유지한다.

## 12. DB 개발 순서 제안

1. 현재 스키마와 추가 요구사항 비교
2. 사용자 권한과 종목 마스터 확정
3. 가격·수급 데이터 저장 여부 결정
4. 원문 문서와 RAG 청크 관계 확정
5. 사용자 메모 원본 테이블 확정
6. 시장 심리·근거 강도 스냅샷 설계
7. 분석 실행·근거 추적 구조 설계
8. Redis와 영구 DB 데이터 경계 확정
9. 삼성전자 시드 데이터로 조회 테스트
10. 실제 API 응답에 맞춰 컬럼 조정

## 13. DB 회의 질문

- 가격 시계열을 DB에 저장할지 API와 Redis만 사용할지 <스크래핑하는 프로그램을 짜서 15분마다 긁어 DB에 저장. 종목 입력받으면 검색 후 LLM을 이용하여 요약 후 프론트에 3줄 출력>
- 투자자별 수급의 기준 주기와 단위를 무엇으로 할지 
- 뉴스 원문 전체를 저장할 수 있는지 
- 원문 문서 테이블을 별도로 둘지 <O>
- 사용자 메모를 일반 테이블과 RAG에 함께 관리할지 
- 시장 심리 온도와 근거 강도를 어떤 주기로 저장할지 
- 점수 계산 버전을 어떻게 관리할지 
- 분석 답변과 사용 근거를 얼마나 오래 보관할지 <알아서 자동 삭제 AI추천>
- Backend와 MCP가 사용하는 DB 권한을 어떻게 나눌지
- 실제 데이터가 없는 개발 환경에서 어떤 시드 데이터를 사용할지
