# stock_insight 프로젝트 전체 방향 제안서

> 이 문서는 팀 회의를 위한 설계 초안입니다. 아래 내용은 확정된 요구사항이 아니며, 실제 데이터 확보 가능성·개발 기간·팀 역할을 확인한 뒤 수정할 수 있습니다.

## 1. 우리가 만들려는 서비스

`stock_insight`는 종목을 추천하거나 주가를 예측하는 서비스가 아니다.

사용자가 급등·급락한 종목을 보고 충동적으로 매매하기 전에, 가격 뒤에서 어떤 일이 일어나고 있는지 확인할 수 있도록 돕는 **종목별 시장 맥락 분석 플랫폼**을 목표로 한다.

### 한 문장 정의

> 종목을 검색하면 가격·거래량·투자자별 수급·뉴스·공시·커뮤니티 반응을 연결하여, 시장의 공포와 탐욕이 어디서 나왔고 그 기대에 확인된 근거가 있는지를 설명하는 서비스

### 해결하려는 문제

기존 증권 서비스에도 현재가, 뉴스, 공시, 수급, 종목토론방은 존재한다. 하지만 정보가 서로 분리되어 있기 때문에 사용자가 직접 여러 화면을 오가며 관계를 판단해야 한다.

예를 들어 삼성전자가 하루 만에 크게 상승했을 때 사용자는 다음 내용을 따로 확인해야 한다.

- 가격과 거래량이 평소보다 얼마나 크게 움직였는가?
- 개인·외국인·기관 중 누가 사고팔았는가?
- 커뮤니티에서는 어떤 기대가 퍼지고 있는가?
- 뉴스는 어떤 이슈를 다루고 있는가?
- DART에 공식적으로 확인된 공시가 있는가?
- 시장의 기대가 사실보다 앞서고 있는가?

우리 서비스는 이 자료를 한곳에 모으는 것에서 끝나지 않고, 자료가 서로 일치하는지 또는 충돌하는지를 설명한다.

## 2. 핵심 결과: 시장 심리 온도와 근거 강도

한 개의 불투명한 점수로 매수·매도를 암시하지 않고, 서로 다른 성격의 두 지표를 분리해서 보여주는 방향을 제안한다.

| 지표 | 의미 | 주요 근거 |
|---|---|---|
| 시장 심리 온도 | 시장 참여자들이 공포 또는 탐욕 중 어느 쪽에 가까운지 | 커뮤니티 감성, 언급량, 가격·거래량 변화, 개인 수급, 뉴스 분위기 |
| 근거 강도 | 현재 기대나 공포가 공식적·객관적 자료로 얼마나 확인되는지 | DART 공시, 재무 수치, 공식 발표, 수급 일치 여부, 출처 신뢰도와 최신성 |

두 지표의 조합은 다음처럼 해석할 수 있다.

| 조합 | 사용자에게 제공할 해석 예시 |
|---|---|
| 탐욕 높음 + 근거 높음 | 긍정적인 재료가 확인되며 시장의 기대도 강한 상태 |
| 탐욕 높음 + 근거 낮음 | 시장의 기대와 관심이 확인된 사실보다 앞서는 상태 |
| 공포 높음 + 근거 높음 | 실제 위험 요소가 확인되며 우려가 커진 상태 |
| 공포 높음 + 근거 낮음 | 뚜렷한 악재보다 심리적인 공포가 크게 작용한 상태 |

점수 옆에는 반드시 계산 기준, 데이터 기준 시각, 근거 출처를 함께 표시한다.

## 3. 대표 사용자 시나리오

첫 번째 완성 목표는 아래 흐름 하나를 끝까지 동작시키는 것이다.

1. 사용자가 로그인한다.
2. `삼성전자`를 검색한다.
3. 현재가, 최근 등락, 거래량 변화를 확인한다.
4. 개인·외국인·기관 수급을 확인한다.
5. 시장 심리 온도와 근거 강도를 확인한다.
6. 주요 뉴스·공시·커뮤니티 주제를 확인한다.
7. 사용자가 `오늘 삼성전자는 왜 올랐어?`라고 질문한다.
8. AI Agent가 질문에 필요한 MCP 도구를 선택한다.
9. 가격·수급·뉴스·공시·RAG 검색 결과를 근거로 답변한다.
10. 답변에는 출처와 데이터 기준 시각이 표시된다.
11. 사용자는 자신의 매수 근거·우려·확인 조건을 투자 메모로 저장한다.
12. 이후 `내가 작성한 우려와 최근 상황을 비교해줘`라고 질문할 수 있다.

## 4. 서비스가 하지 않는 일

- 특정 종목 매수·매도 추천
- 목표주가 또는 미래 수익률 보장
- AI가 근거 없이 주가 상승·하락 원인을 단정
- 커뮤니티 의견을 사실로 취급
- 오래된 정보를 최신 정보처럼 표시
- 처음부터 모든 종목과 모든 커뮤니티 기능 구현

AI 답변에서는 `이 뉴스 때문에 주가가 올랐다`라고 단정하기보다 `같은 시점에 확인된 주요 상승 관련 재료`처럼 사실과 해석을 구분한다.

## 5. 전체 시스템 연결 구조

```text
[사용자]
   │ 종목 검색·질문·투자 메모
   ▼
[Frontend / Streamlit]
   │ HTTP 요청 + SSE 진행 이벤트
   ▼
[Backend / FastAPI]
   ├─ 로그인·권한·요청 검증
   ├─ Redis 캐시 확인
   ├─ AI Agent 실행
   └─ 최종 응답 조립 및 기록
             │ MCP 호출
             ▼
[MCP Server / FastMCP]
   ├─ 종목 검색 Tool
   ├─ 가격·거래량 Tool
   ├─ 투자자별 수급 Tool
   ├─ 뉴스 Tool
   ├─ DART 공시·재무 Tool
   ├─ 커뮤니티 분석 Tool
   └─ RAG·사용자 메모 검색 Tool
             │
      ┌──────┴───────────┐
      ▼                  ▼
[외부 데이터 제공처]  [PostgreSQL + pgvector]

[Redis]
   ├─ 시세·뉴스·질문 결과 캐시
   └─ 분석 작업·SSE 진행 상태
```

### 책임 분리 원칙

- Frontend는 Backend에만 요청하고 DB나 외부 API에 직접 접근하지 않는다.
- Backend는 인증, 권한, Agent 실행, SSE, 최종 응답을 담당한다.
- MCP Server는 투자 정보 조회와 RAG 검색 기능을 Tool로 제공한다.
- PostgreSQL은 영구 데이터, Redis는 짧게 유지할 캐시와 진행 상태를 담당한다.
- LLM은 MCP가 제공한 근거를 설명하는 역할이며 사실 데이터의 원천이 아니다.

## 6. 두 가지 데이터 흐름

### 6.1 수집·가공 흐름

뉴스, 공시, 커뮤니티처럼 미리 준비할 데이터는 사용자 질문과 분리하여 수집한다.

```text
외부 데이터
  → 수집
  → 형식 통일
  → 중복 제거
  → 종목코드 연결
  → 일반 DB 원문·수치 저장
  → 긴 문서 청킹
  → 임베딩 생성
  → pgvector 저장
  → 시장 심리 온도·근거 요소 계산
```

### 6.2 사용자 질문 흐름

```text
질문
  → Backend 인증·검증
  → Redis 캐시 확인
  → Agent가 필요한 도구 결정
  → MCP Tool 호출
  → 가격·수급·뉴스·공시·RAG 근거 취합
  → LLM이 사실과 해석을 구분하여 설명
  → 출처·기준 시각과 함께 저장 및 반환
```

## 7. 필요한 정보

| 정보 | 예시 | 저장·조회 방향 |
|---|---|---|
| 종목 기본정보 | 종목코드, 기업명, 시장, 업종, DART 기업번호 | 일반 DB |
| 가격·거래량 | 현재가, 등락률, 거래량, 가격 시계열 | API 조회 + 일반 DB/Redis 캐시 |
| 투자자별 수급 | 개인·외국인·기관 순매수 | 일반 DB 또는 API 조회 |
| 뉴스 | 제목, 내용, 언론사, 발행시각, URL, 관련 이슈 | 원문 메타데이터 + RAG |
| 공시·재무 | 공시 제목·본문, 실적, 사업 방향, 위험요인 | 수치는 일반 DB, 본문은 RAG |
| 커뮤니티 | 게시글, 반응, 언급량, 감성, 주요 주제 | 요약 수치는 일반 DB, 내용은 RAG |
| 사용자 정보 | 권한, 관심 종목, 투자 메모, 질문 기록 | 일반 DB + 메모 RAG |

데이터 제공처와 수집 주기는 실제 접근 가능성, 비용, 이용 조건을 확인한 뒤 결정한다. 특히 특정 증권 커뮤니티 데이터는 수집 가능 여부를 먼저 검증하고, 실패할 경우 데모 데이터 또는 이용 가능한 대체 자료로 교체할 수 있게 한다.

## 8. 수업 요구사항과 프로젝트 적용

| 수업 요소 | 프로젝트 적용 예시 |
|---|---|
| Frontend | 로그인, 검색, 종목 분석, 질문, 관리자 화면 |
| Backend | 인증, Agent 오케스트레이션, SSE, 응답 기록 |
| MCP Server | 시세·뉴스·공시·커뮤니티·RAG Tool |
| Database | 사용자·종목·수급·문서·분석 결과 저장 |
| Redis | 반복 조회 캐시, 진행 상태 |
| RAG | 뉴스·공시·커뮤니티·사용자 메모 검색 |
| AI Agent | 질문에 따라 필요한 도구 선택 |
| SSE | `뉴스 검색 중`, `공시 분석 중` 등의 진행 표시 |
| Admin/User | 자료 관리와 일반 분석 기능 분리 |
| Multimodal | IR·실적발표 MP3/MOV를 텍스트로 변환하여 RAG에 저장 |
| System Architecture | 각 서버를 독립 실행하고 환경변수로 주소 연결 |

## 9. 단계별 개발 제안

### 1단계: 최소 연결 확인

- Frontend → Backend → MCP → DB → Frontend 왕복
- Redis 연결
- 실제 데이터 대신 삼성전자 샘플 데이터를 사용해도 됨
- 각 컴포넌트를 서로 다른 컴퓨터에서 실행 가능한지 확인

### 2단계: 핵심 정보 Tool

- 종목 검색
- 가격·거래량
- 투자자별 수급
- 뉴스
- DART 공시

### 3단계: RAG와 Agent

- 뉴스·공시 청킹 및 임베딩
- 종목·문서 종류 선필터 후 벡터 검색
- 질문별 Tool 선택
- 근거와 출처가 포함된 답변

### 4단계: 시장 심리 분석

- 커뮤니티 데이터 확보 가능성 검증
- 감성·언급량·주제 계산
- 시장 심리 온도와 근거 강도 설계
- 지표의 계산 근거 표시

### 5단계: 사용자 기능

- 회원가입·로그인
- Admin/User 권한
- 관심 종목
- 투자 메모
- 질문·답변 기록

### 6단계: 사용성 및 확장

- Redis 캐시
- SSE 진행 상태
- 관리자 RAG 자료 등록
- MP3/MOV 텍스트 변환
- 종목별 사용자 커뮤니티는 시간이 남을 경우 검토

## 10. 1차 MVP 제안

한 달 프로젝트의 우선 범위를 다음과 같이 제안한다.

- 삼성전자 중심 데모 후 제한된 종목으로 확장
- 로그인
- 종목 검색
- 가격·거래량·투자자별 수급
- 뉴스·DART 공시
- 커뮤니티 시장 심리 요약
- 시장 심리 온도와 근거 강도
- 근거 기반 AI 질문
- 사용자 투자 메모
- Redis 캐시와 SSE 진행 표시
- 출처와 데이터 기준 시각 표시

종목별 방, 게시글, 댓글, 정교한 포트폴리오 분석은 핵심 흐름이 완성된 뒤 확장 여부를 결정한다.

## 11. 팀 회의에서 확정할 사항
